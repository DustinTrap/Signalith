    Releasing¶

    How a Signalith release is made, for maintainers. Users want Install from packages.

    What a release contains¶

    The Release workflow (.github/workflows/release.yml) runs when a tag such as v0.1.0 is pushed. It:

    1. Builds the programs for Linux (amd64, arm64) and Windows (amd64), the .deb and .rpm packages (deploy/packages, built with nFPM) and the .msi (deploy/windows/msi, built with the WiX Toolset v5).
    2. Tests each package: installs the latest earlier release, upgrades it to the new one, signs in, removes it and installs it again, on Ubuntu with systemd, in Rocky Linux 9 and Fedora containers, and on Windows Server. CI runs the same tests on every pull request (the Packages workflow), upgrading from the latest release.
    3. Builds the container image for amd64 and arm64, pushes it to ghcr.io/jrsamsanchez/signalith:<version> (and :latest unless the version has a - suffix such as -rc.1), signs it with Sigstore and attaches its SBOM and provenance. (Between releases, the Image (main) workflow publishes the same kind of signed image as :main on every push to main; the Docker quick start runs it.)
    4. Writes the SBOM (SPDX and CycloneDX, made by Syft from the Linux program), SHA256SUMS, its Sigstore signature, its GPG signature when the key is set up (below), and GitHub build provenance for every file.
    5. Publishes it all on the Releases page, with install and verify steps (.github/release-notes.md) above the generated list of changes. A version with a - suffix is marked as a pre-release.
    6. Once it has published, the Website workflow adds the new packages to the apt and dnf repositories on signalith.io (below), so apt upgrade and dnf upgrade find them.

    Run workflow on the Release workflow's page (Actions > Release) is a dry run: it builds and tests everything for the version you enter and keeps the files as a workflow artifact named release, and publishes nothing.

    Making a release¶

    1. Make sure CI is green on main.

    2. Tag and push:

      git checkout main && git pull
git tag -a v0.1.0 -m "Signalith 0.1.0"
git push origin v0.1.0

    3. Watch Actions > Release. When it is green, the release is on the Releases page and the image on GHCR.

    The first time an image is pushed, check that the package is public: the repository's Packages list > signalith > Package settings > Change visibility > Public.

    Signing keys¶

    Every release is signed with Sigstore and has GitHub build provenance without any setup: GitHub vouches for the workflow that built it.

    GPG (Linux packages and checksums)¶

    apt, dnf and rpm check packages with GPG keys. When the repository has a SIGNALITH_GPG_PRIVATE_KEY secret, the .rpm and .deb packages and SHA256SUMS are signed with it, and the public key is published with each release as signalith-release-key.asc. It also signs the apt and dnf repositories at https://signalith.io/apt and https://signalith.io/rpm, which the Website workflow rebuilds from the five newest releases after every Release run (deploy/repos/build.sh; packages from before the key existed are signed there). Until the secret is set, the website has no repositories.

    To make the key (with Docker, on any computer), in an empty folder:

    docker run --rm -v "${PWD}:/out" alpine:3.20 sh -c "apk add -q gnupg && gpg --batch --passphrase '' --quick-gen-key 'Signalith releases <releases@signalith.io>' rsa4096 sign 3y && gpg --armor --export-secret-keys > /out/signalith-release-private.asc && gpg --armor --export > /out/signalith-release-key.asc"

    Then on GitHub: the repository's Settings > Secrets and variables > Actions > New repository secret, name SIGNALITH_GPG_PRIVATE_KEY, and paste the whole of signalith-release-private.asc (from -----BEGIN to the last -----). Keep a copy of that file somewhere safe and offline, then delete it from the computer. If the key has a passphrase, add it as SIGNALITH_GPG_PASSPHRASE. The key expires after three years; make a new one before then.

    Content updates¶

    The weekly Content workflow (.github/workflows/content.yml) rebuilds the SigmaHQ and Splunk packs from the newest upstream rules, runs every pack check, and publishes them as a signed bundle on the content release, which servers check for (see Content updates). It signs with an Ed25519 key in the SIGNALITH_CONTENT_KEY secret; without the secret it builds and tests but publishes nothing. Servers only take bundles signed by a key listed in internal/content/trusted.keys, so a new key reaches them with the next release.

    To make the key (with Docker, on any computer; the same line works in PowerShell):

    docker run --rm alpine:3.20 sh -c 'apk add -q openssl && openssl genpkey -algorithm ed25519 -outform DER -out /k && echo private: $(tail -c 32 /k | base64) && echo public: $(openssl pkey -inform DER -in /k -pubout -outform DER | tail -c 32 | base64)'

    (signalith content keygen prints the same pair.) Then on GitHub: the repository's Settings > Secrets and variables > Actions > New repository secret, name SIGNALITH_CONTENT_KEY, and paste the private key line. Add the public key line to internal/content/trusted.keys (the workflow log also prints it, and warns while it is missing). Keep a copy of the private key somewhere safe and offline. To replace a key, add the new public key next to the old one, release, switch the secret, and remove the old key in a later release.

    Windows code signing¶

    The Release workflow signs the .msi and signalith-windows-amd64.exe with Authenticode through SignPath Foundation, which signs open-source projects for free; the code signing policy is the page it asks projects to publish. Until SignPath is set up, the Windows files are released unsigned and SmartScreen warns before running the installer.

    To set it up:

    1. Apply at signpath.org for the Signalith repository.
    2. Once accepted, in SignPath: create the project signalith, connect it to GitHub as its trusted build system, add the artifact configuration from deploy/windows/signpath/artifact-configuration.xml, and create the signing policy release-signing with yourself as approver. Make an API token for a CI user that may submit requests.
    3. On GitHub, Settings > Secrets and variables > Actions: add the secret SIGNPATH_API_TOKEN, and on the Variables tab the variable SIGNPATH_ORGANIZATION_ID. (SIGNPATH_PROJECT_SLUG and SIGNPATH_SIGNING_POLICY_SLUG change the two names above if you chose others.)

    From then on, each release run sends the two files to SignPath and waits up to four hours for you to approve the request there (SignPath emails you), checks the signatures on Windows, and publishes the signed files. Every signalith.exe carries its name and version (made by go-winres at build time), which the artifact configuration requires.

    Version numbers¶

    Versions are MAJOR.MINOR.PATCH, with an optional -rc.N style suffix for pre-releases. Windows Installer uses only the three numbers, so a pre-release and its final release share an MSI version; the installer allows that, and the final one replaces the pre-release.

    Licences of the build tools¶

    nFPM (MIT), Syft (Apache 2.0), Sigstore cosign (Apache 2.0) and MkDocs Material (MIT) are open source. The WiX Toolset is MS-RL; from v6 its prebuilt binaries come with an Open Source Maintenance Fee agreement for revenue-making users, so the build pins WiX v5, which has none. None of these tools is shipped inside Signalith.
